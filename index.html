Operating Systems Core Concepts: Disk Scheduling & Concurrency
Disk Cylinders & Physical Geometry

A hard disk comprises circular platters spinning at high speeds (e.g., 7200 RPM). A cylinder represents the set of all tracks across multiple platter surfaces located at the same radial distance from the spindle. All read/write heads move simultaneously on a rigid actuator arm.

Seek Time vs. Total Access Time

Disk access time consists of Seek Time + Rotational Latency + Transfer Time. Mechanical Seek Time (moving the physical arm across cylinders) is the slowest mechanical phase (~3-10ms), making seek-minimization the primary objective of disk scheduling algorithms.

Why Web Workers in ThreadSeek?

Standard JavaScript in web browsers runs on a single main UI thread. ThreadSeek spawns five independent Web Workers via Blob URLs. Each worker calculates its algorithm's seek order in an isolated background thread without freezing animations, passing results via postMessage().

Selection Rule: Requests are processed strictly in the chronological order of their arrival in the I/O queue.

Direction / Boundary Behavior: Head moves directly from current cylinder to the next queued cylinder without regard for direction or disk boundaries.

Advantages: Absolutely fair to all processes; zero risk of starvation; computationally trivial with O(1) queue dispatch.

Disadvantages: Produces erratic, wild head swings (ping-pong effect), resulting in massive seek distances and poor disk throughput.

When to Use: Light workloads where queue depth is negligible, or real-time FIFO requirements.

Selection Rule: From the current head position, the scheduler chooses the pending cylinder request with the minimum absolute distance: min(|current_head - request_i|).

Tie-Breaking Rule in ThreadSeek: When two requests are equidistant from the head, the algorithm chooses the request along the current traversal direction; if neither applies, it picks the lower cylinder number.

Advantages: Substantially reduces total head movement compared to FCFS; delivers high throughput for dense workloads.

Disadvantages (Critical Viva Concept): Starvation / Arm Stickiness! Outlying cylinders (e.g. tracks near 0 or maximum cylinder) may wait indefinitely if incoming requests cluster tightly around the current head position.

Selection Rule: Mimics an elevator building lift: the head moves continuously in one direction (e.g., Right / Increasing), servicing any pending requests in its path until it touches the disk boundary (cylinder disk_size - 1 or 0), then reverses direction and services requests on the return sweep.

Boundary Behavior: Textbook SCAN always travels to the physical boundary before reversing.

Advantages: Eliminates indefinite starvation; upper bound on waiting time is roughly twice the sweep across the disk.

Disadvantages: Requests near the recently visited end experience longer wait times than requests in the center; unnecessary travel to disk boundaries when no requests reside there.

Selection Rule: Like SCAN, it sweeps in a single direction servicing requests up to the boundary. However, once it reaches the end, it immediately executes a fast return circular jump back to the opposite boundary without servicing requests on the return sweep, then resumes servicing in the initial forward direction.

Special Jump Treatment: The return jump is purely an arm repositioning move (often accomplished at maximum actuator velocity). In many OS textbooks (e.g., Silberschatz), the circular jump distance (e.g. disk_size - 1) can either be counted or excluded. Advantages: Provides a much more uniform waiting time distribution than SCAN across all cylinders.

Selection Rule: The head "looks" ahead in the current direction. It moves in that direction servicing requests, but reverses as soon as there are no further pending requests in that direction, rather than proceeding all the way to the disk boundary (0 or 199).

Advantages: Avoids the wasted seek movements to cylinder 0 or disk maximum, almost always achieving lower head movement than SCAN while retaining starvation avoidance.

Q1. What is disk scheduling and why is it necessary?
Disk scheduling is the technique employed by the operating system to order the pending I/O read and write requests for secondary storage. It is essential because mechanical disk head seek time is several orders of magnitude slower than electronic RAM access. Scheduling optimizes the sequence to minimize total head travel, maximize throughput, and ensure fair request service.
Q2. What is seek time?
Seek time is the time taken by the disk read/write actuator arm to physically accelerate, travel across platters, and settle upon the specified cylinder/track containing the desired data sector. It is the dominant latency component in magnetic hard drives.
Q3. What is head movement in disk scheduling calculations?
Head movement is the total number of cylinders traversed by the read/write head while servicing a sequence of requests. It is calculated as the sum of absolute cylinder differences: ∑ |Current_Cylinder - Next_Cylinder|. Lower head movement directly correlates to reduced mechanical wear and faster response.
Q4. What is the FCFS disk scheduling algorithm?
First-Come, First-Served (FCFS) processes disk requests strictly in the order they arrive in the I/O queue. While it is completely fair and free of starvation, it frequently produces wild head oscillations back and forth across platters, yielding the highest total head movement.
Q5. What is SSTF and what is its fundamental principle?
Shortest Seek Time First (SSTF) is a greedy heuristic that selects the pending request closest to the current disk head position: min(|head - request|). This minimizes immediate seek distance at every step.
Q6. What is the starvation problem (arm stickiness) in SSTF?
Starvation occurs in SSTF when a continuous stream of new requests arrives near the current head position. The head remains confined in that local cylinder cluster (arm stickiness), while requests situated far away at the inner or outer disk edges are starved of service indefinitely.
Q7. What is the SCAN (Elevator) algorithm?
SCAN operates like a building elevator: the disk head starts at the initial cylinder and travels in a single direction (e.g. increasing), servicing requests until it reaches the physical disk boundary (cylinder 0 or max). At the boundary, it reverses direction and sweeps back, servicing requests encountered on the return journey.
Q8. How does C-SCAN differ from SCAN?
In standard SCAN, the head reverses and services requests in both directions. In Circular SCAN (C-SCAN), the head services requests in one direction only. When it reaches the boundary, it executes an immediate return jump to the opposite boundary without servicing requests on the way, providing a uniform waiting time across all cylinders.
Q9. How does LOOK differ from SCAN?
SCAN always travels to the physical boundary (0 or disk size - 1) before reversing. LOOK "looks" ahead at the pending queue and reverses immediately at the furthest pending request in that direction, avoiding wasted seek motion to empty boundary cylinders.
Q10. What is a disk cylinder?
A cylinder is the collection of all circular tracks on all platter surfaces that lie at the exact same radial distance from the spindle center. Because the heads on all platter arms move simultaneously, data on the same cylinder can be accessed across surfaces without moving the physical actuator arm.
Q11. Why do different disk scheduling algorithms produce different total head movements?
They employ distinct optimization policies: FCFS prioritizes arrival order; SSTF prioritizes local proximity; SCAN enforces directional sweeps to bounds; LOOK truncates directional sweeps; and C-SCAN enforces unidirectional fairness. These differing trajectories traverse different permutations of cylinder intervals.
Q12. What is multithreading in an Operating System?
Multithreading is the capability of a CPU or single process to execute multiple concurrent threads of instructions independently. Threads share the address space, open files, and memory of their parent process while maintaining their own registers, program counter, and stack.
Q13. What is a Web Worker in modern browsers?
A Web Worker is an isolated native browser background thread that runs JavaScript code parallel to the main UI event loop. Because it operates in a separate execution context, heavy computations running inside a Web Worker never block user interactions, CSS animations, or UI rendering.
Q14. Why does ThreadSeek use five independent Web Workers?
ThreadSeek assigns each of the five scheduling algorithms (FCFS, SSTF, SCAN, C-SCAN, LOOK) to its own dedicated worker thread (e.g. FCFS-thread). This demonstrates genuine parallel multi-agent computation: all five compute their seek trajectories simultaneously in background threads, reporting progress and results via asynchronous messages.
Q15. What is the difference between worker execution and visual animation?
Web Worker execution happens in microseconds on CPU threads, purely computing mathematics and path arrays. Visual animation, on the other hand, is a pedagogical UI simulation displayed on the screen at human-observable speeds (e.g. 500ms per step) to help students visualize the mechanical disk head traversing cylinders.
Q16. Why is postMessage() used for Web Worker communication?
Web Workers do not have access to the DOM, window object, or main thread memory. They communicate strictly via asynchronous, isolated message passing using worker.postMessage() and onmessage event handlers, passing serialized structured data safely across thread boundaries.
Q17. What is the role of Promise.all() in ThreadSeek?
Promise.all() acts as a thread barrier/synchronization join mechanism. It takes the five promises representing the dispatched Web Workers and resolves only when all five worker threads have completed their tasks, allowing the application to aggregate results, build the comparison table, and declare the winner synchronously.
Q18. What happens if one worker thread fails or throws an error?
ThreadSeek implements robust error isolation: each worker has its own onerror listener and try-catch envelope. If one algorithm thread encounters an exception, its status card updates to Error without crashing or corrupting the calculations of the remaining four healthy worker threads.
Q19. Why is C-SCAN's circular return jump treated specially?
The return jump is an arm reset across the entire platter without read/write activity. In academic literature, some authors (like Silberschatz) count the jump distance in total seek movement, while other textbooks exclude it because no data is transferred. ThreadSeek supports both conventions via a configuration toggle!

Q21. What is rotational latency and how does it relate to RPM?
Rotational latency is the delay waiting for the desired sector to rotate under the read/write head once the head has reached the target cylinder. On average, it equals half a revolution: Latency = 0.5 × (60 / RPM) seconds. For a 7200 RPM drive, average rotational latency is approximately 4.16ms.
